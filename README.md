# claude-settings

Внутренний маркетплейс плагинов Claude Code для проектов JVD-Soft.

Существует по одной причине: агентная конфигурация была скопирована побайтово
в каждый репозиторий и расходилась молча. Цена уже была уплачена — миграцию
фронтенда на TypeScript сделали дважды, независимо, разными коммитами. Здесь
общий слой живёт в одном месте и версионируется.

## Что внутри

`plugins/jvd-frontend` — для стека Laravel + React/Vite:

| | |
|---|---|
| `skills/scaffold` | Поднимает фронтенд проекта до базовой линии стека: харнес Vitest, error boundaries, safeStorage, SEO и пререндер, PWA, заголовки nginx, CI, цели Makefile. ~35 файлов и 8 слияний одной командой. Режим `--brand` переименовывает форк. |
| `commands/new-project` | Порядок заведения нового проекта: форк `base_setup` → `--brand` → бэкенд-слоты → `make init` → `make check`. |
| `hooks/detect-setup.mjs` | `SessionStart`: говорит, чего из базовой линии не хватает. Молчит, когда всё на месте. |
| `hooks/guard-read.mjs` | `PreToolUse`: не даёт прочитать сборку, зависимости, лок-файлы и бинарники целиком. 49 самотестов. |
| `hooks/format-changed.mjs` | `PostToolUse`: `eslint --fix` на один изменённый файл. Раньше это была просьба к агенту не забыть. |
| `agents/jvd-frontend-reviewer` | Ревью изменения против конвенций стека. |
| `agents/jvd-a11y-auditor` | То, что линтер структурно не видит: доступные имена, фокус, лендмарки. |
| `agents/jvd-test-writer` | Тесты по конвенциям харнеса Vitest + RTL. |
| `agents/jvd-prerender-doctor` | Разбор упавшего или пустого пререндера. |
| `skills/` | `react-data-fetching`, `shadcn-ui-components`, `forms-validation`, `i18n-translations`. |
| `.mcp.json` | `context7` (документация вместо памяти модели) и `shadcn`. |

`plugins/jvd-backend` — для Laravel-половины того же стека:

| | |
|---|---|
| `skills/laravel-api-endpoint` | Как добавить эндпоинт: тонкий контроллер на абстрактной базе, сервис с доменными значениями, FormRequest для валидации, конверт ответа, числовые уровни ролей, паритет `lang/`. |

Плагины независимы: фронтендный проект включает только `jvd-frontend`, бэкендный
— только `jvd-backend`, монорепо вроде `base_setup` — оба.

## Как пользоваться

Всё из плагина вызывается **с неймспейсом** плагина — `jvd-frontend:` или
`jvd-backend:`, — без него имени просто нет. Это же и защита: одноимённая
команда проекта не перекроет плагинную.

### Команды

| | |
|---|---|
| `/jvd-frontend:new-project [имя]` | Завести новый проект: форк `base_setup` → `--brand` → бэкенд-слоты → `make init` → `make check`. Спрашивает перед клонированием, ремоутами и `make init`. |
| `/jvd-frontend:check` | Полный гейт: lint, typecheck, тесты, build — те же четыре шага, что и CI. |
| `/jvd-frontend:sync-from-template` | Перенести изменение из `base_setup` в форк или посмотреть, что разошлось. |
| `/jvd-frontend:verify-hooks` | Проверить, что read-guard всё ещё блокирует сборку и всё ещё пропускает исходники. |

### Скилы

**Сами активируются** по описанию — `forms-validation` при работе с формой,
`i18n-translations` при любом пользовательском тексте, `react-data-fetching`
при запросе к API, `shadcn-ui-components` при работе с примитивами,
`laravel-api-endpoint` при работе в `backend/`. Ничего вызывать не нужно; они
появляются в контексте, когда задача их касается.

Явно — по имени, если нужен именно он:

```
/jvd-frontend:scaffold
```

`scaffold` — единственный, который обычно зовут руками: он не «знание», а
действие. Скрипт под ним можно запустить и напрямую:

```bash
node "$CLAUDE_PLUGIN_ROOT/skills/scaffold/scripts/scaffold.mjs" --dry-run
```

| Флаг | Что делает |
|---|---|
| `--dry-run` | Печатает план, не пишет ничего. Всегда начинайте с него. |
| `--brand` | Отдельный режим: переименовывает форк под новый продукт. |
| `--force` | Берёт шаблонную версию seeded-файла. Только если проектная — стоковый Vite или устаревшая база. |
| `--accept` | Оставляет проектную версию и запоминает, с какой версией шаблона её сравнивали. Строка перестаёт повторяться. |
| `--set KEY=VALUE` | Переопределить одно значение для пробного прогона. |

### Агенты

Зовутся по имени, когда нужен отдельный проход по узкой теме:

`jvd-frontend-reviewer` — ревью изменения против конвенций стека ·
`jvd-a11y-auditor` — доступные имена, фокус, лендмарки ·
`jvd-test-writer` — тесты по конвенциям Vitest + RTL ·
`jvd-prerender-doctor` — упавший или пустой пререндер.

### Хуки — работают сами

`SessionStart` в начале сессии говорит, чего не хватает, и молчит, когда всё на
месте. `PreToolUse` не даёт прочитать сборку и лок-файлы целиком. `PostToolUse`
прогоняет `eslint --fix` по одному изменённому файлу.

**Префикс `jvd-` у агентов обязателен.** Плагинные агенты — самый низкий из
пяти уровней приоритета: одноимённый файл в `.claude/agents/` проекта молча
перекрывает плагинный, без ошибки и без следа. `scripts/validate-plugins.mjs`
падает на агенте без префикса.

**Хуки и агенты — только фронтендные.** `jvd-backend` не поставляет ни хуков, ни
агентов, ни MCP: read-guard, format-on-edit и четыре агента живут в
`jvd-frontend` и включаются вместе с ним.

## Подключение

Репозиторий приватный, поэтому Claude Code клонирует его вашими git-креденшелами.
Убедитесь, что `git clone https://github.com/JVD-Soft/claude-settings.git`
проходит без запроса пароля (Git Credential Manager на Windows или `gh auth login`).

Дальше — два файла, и разница между ними определяет, где плагин работает.

### Один раз на машину — дальше работает в любом проекте

В `~/.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "jvd-soft": {
      "source": { "source": "github", "repo": "JVD-Soft/claude-settings" }
    }
  },
  "enabledPlugins": {
    "jvd-frontend@jvd-soft": true,
    "jvd-backend@jvd-soft": true,
    "typescript-lsp@claude-plugins-official": true
  }
}
```

После этого в новом проекте делать не нужно **ничего** — Claude Code ставит
плагин сам при первом запуске в этой папке. `typescript-lsp` объявлен в
`dependencies` плагина, но зависимости не доставляются автоматически: пока его
не включить рядом, TS-подсказок от LSP не будет.

Ставить через `/plugin` в конкретном проекте — не то же самое. Такая установка
получает `"scope": "project"` и привязку к пути в `installed_plugins.json`, то
есть в соседней папке плагина просто нет.

### В репозитории — чтобы то же самое получили коллеги

Тот же блок в `.claude/settings.json` проекта. Он коммитится, поэтому любой,
кто склонировал репозиторий, получает ту же конфигурацию. Держать оба файла —
норма, а не дублирование: пользовательский закрывает новые проекты, проектный —
чужие клоны. Но описание маркетплейса в них должно совпадать буквально:
`{"source": "github", "repo": …}` в одном и `{"source": "git", "url": …}` в
другом — это два разных определения одного имени.

Оба ключа — объекты, не массивы. Имя маркетплейса (`jvd-soft`) должно
совпадать с `name` в `.claude-plugin/marketplace.json`, иначе ссылки
`jvd-frontend@jvd-soft` и `jvd-backend@jvd-soft` никуда не ведут.

### Перезагрузка — обязательный шаг, а не «на всякий случай»

Команды, скилы, агенты, хуки и MCP-серверы привязываются **при старте
процесса**. Правка `settings.json` на живой сессии плагин установит — файлы
появятся в `~/.claude/plugins/`, — но в этой сессии не появится ничего:
`/plugin` покажет плагин включённым, а `/jvd-frontend:scaffold` не найдётся.
Новый чат не помогает, процесс тот же.

- `/reload-plugins` — перечитать плагины, не выходя;
- расширение VS Code: `Ctrl+Shift+P` → **Developer: Reload Window**;
- CLI: выйти и запустить `claude` заново.

### Ловушка: тумблер в `/plugin` пишет в текущий проект

Выключение плагина через `/plugin` записывает `"jvd-frontend@jvd-soft": false`
в `.claude/settings.json` **этого проекта**. Проектные настройки приоритетнее
пользовательских, поэтому один клик во время «сейчас проверю» молча оставляет
плагин выключенным в этом репозитории — при том, что на машине он включён. Если
плагина нет ровно в одном проекте, сначала откройте этот файл и посмотрите на
значение, а не переустанавливайте.

### Проверить, что поднялось

`/plugin` показывает маркетплейс и включённые плагины · скилы видны под
неймспейсами `jvd-frontend:` и `jvd-backend:` · `/mcp` — оба сервера ·
`/jvd-frontend:verify-hooks` — что read-guard жив.

**Режим отказа тихий.** Если репозиторий недоступен, плагина просто нет — агент
ведёт себя как со старым конфигом, без ошибки. Если хук перестал срабатывать
или пропали MCP-серверы, порядок проверки такой: перезагрузка → значение в
`.claude/settings.json` проекта → доступ к репозиторию.

## Настройка под проект

Восемь значений (`APP_NAME`, `APP_SHORT_NAME`, `APP_DESCRIPTION`, `SITE_URL`,
`LANG`, `THEME_COLOR_LIGHT`, `THEME_COLOR_DARK`, `PWA_CATEGORIES`) объявлены
в `userConfig` плагина. Claude Code спрашивает их при включении и отдаёт
скаффолдеру через `CLAUDE_PLUGIN_OPTION_*` — редактировать шаблон под проект
не нужно. Стек один, проекты разные: это ровно та граница между ними.

## Новый проект

Форк `base_setup`, а не пустой репозиторий: файлы, которые ставит скаффолдер,
импортируют `@/api/apiClient`, `@/components/ui`, `@/lib/utils`,
`@/providers/ThemeProvider` и `@/routes` — ничего из этого он не поставляет.
На голом `yarn create vite` `yarn typecheck` падает сразу.

Порядок — в `/jvd-frontend:new-project`. Ключевой шаг, который иначе теряется:
**форк надо переименовать**. Восемь значений `userConfig` бьют в файлы, которые
в форке уже существуют (`index.html`, `app.html`, `vite.config.ts` — seeded,
`config/index.ts` — starter), поэтому обычный прогон их не трогает, и проект
уезжает в прод с `<title>App</title>`. Это делает `--brand`; `SessionStart`
напоминает, если забыли.

## Что сюда НЕ переносится

Роутеры (`AGENTS.md` и вложенные), `docs/context-map.md` и ADR проекта остаются
в проектах. Каждый из них описывает одну конкретную кодовую базу; общий шаблон
таких файлов означал бы, что в одном из проектов документация врёт.

Граница проходит по тому, **что именно** описывает файл. `laravel-api-endpoint`
переехал сюда, потому что описывает конвенции стека — конверт ответа, тонкий
контроллер, уровни ролей, — одинаковые во всех проектах. Состояние конкретного
бэкенда (что сейчас сломано, какие роуты есть) он не описывает и не должен: за
этим он отправляет в `backend/AGENTS.md` проекта.

## Разработка

```bash
node scripts/validate-plugins.mjs
node plugins/jvd-frontend/hooks/guard-read.test.mjs
node plugins/jvd-frontend/skills/scaffold/scripts/scaffold.test.mjs
```

Эти три гоняет CI. `validate-plugins.mjs` существует потому, что структурные
ошибки плагина тихие: сломанный frontmatter не даёт ошибки — скил грузится с
пустыми метаданными и просто перестаёт активироваться сам.

```bash
claude --plugin-dir ./plugins/jvd-frontend
```

`--plugin-dir` перебивает установленную версию на одну сессию. После правок —
`/reload-plugins`.

Версия в `plugin.json` определяет, когда пользователи получат обновление:
поднимайте её осознанно. Без версии считается коммит, и каждый коммит — новая
версия.
